# Release notes template

Every release gets notes with the same sections, so a consumer can read what breaks and what to do before upgrading. The notes have two parts: the sections below, written by the maintainer, and the list of changes, generated by GitHub from the pull request labels (`.github/release.yml`).

Copy the template into the release description, fill the sections and delete the ones that do not apply (keep the headings `Migration`, `Deprecations` and `Compatibility`, even when they say "none").

```markdown
## Highlights

One to three sentences: what this release is about.

## Breaking changes

- What changed, who is affected, and the pull request. (Only in a major version, or in a pre-release before 1.0.)

## Migration

1. The steps to move from the previous version, in order.
2. The codemod command, when there is one.
3. How to check the result (`npm run typecheck`, a test, a screen).

## Deprecations

| Deprecated | Use instead | Removed in |
| --- | --- | --- |
| `OldName` | `NewName` | next major |

The removal version follows the [deprecation policy](deprecation.md).

## Compatibility

Supported Expo, React Native, React and Node versions for this release: [Consumer Compatibility](../compatibility.md).

## What's changed

Generated by GitHub ("Generate release notes"), grouped by label.
```

## Labels and categories

The generated list groups merged pull requests by label, in this order. A pull request appears in the first category it matches; `skip-changelog` removes it from the list.

| Category | Labels |
| --- | --- |
| Breaking changes | `breaking` |
| Migration | `migration` |
| Deprecations | `deprecation` |
| Features | `feature`, `enhancement` |
| Fixes | `bug`, `fix` |
| Documentation | `documentation` |
| Other changes | everything else |

A pull request that changes behaviour for consumers carries a changeset (see `.changeset/README.md` in the repository); the changeset text becomes the entry in `CHANGELOG.md`, and the label decides where the pull request appears in the GitHub notes.

## Changelog generator

`CHANGELOG.md` is written by `changeset version` with `@changesets/changelog-github`, which adds the pull request and author links to each entry. That generator reads the GitHub API, so `GITHUB_TOKEN` must be set when `npm run changeset:version` runs (export a token with read access to the repository; a release workflow must pass the built-in `GITHUB_TOKEN`). The `repo` option in `.changeset/config.json` names the repository and changes with the repository name at the cutover.
